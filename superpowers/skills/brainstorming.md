# Brainstorming —— 需求澄清与设计

## 触发时机

用户提出任何新需求、新想法、或对现有功能的修改诉求，且尚未有批准的设计文档时。
**在任何代码动作之前。**

## HARD-GATE

> 没有经过批准的设计文档，禁止写任何代码、禁止 scaffold 项目、禁止调用任何实施流程。
> 违反字面规则即违反规则精神。

## 流程

### Phase 1：澄清（Socratic 对话）

在提方案前，先弄清：

- 项目当前状态（查 `openspec/specs/` 当前现实）
- 用户想要达成什么目的（而非表面功能）
- 成功标准是什么（可验证的验收条件）

### Phase 2：方案

提出 2–3 个可行方案，说明各自权衡。
推荐一个并说明理由。若方案明显唯一，说明为什么没有别的选择。

### Phase 3：呈现与签字

将设计**逐节呈现**给用户，确认每一步都符合预期。
**必须获得用户明确批准**，未批准不得继续。

### Phase 4：落盘

批准后，将设计写入：

```
superpowers/specs/YYYY-MM-DD-<topic>-design.md
```

## 终态

本 Skill 完成后，唯一允许的下一步是 `writing-plans`（或 openspec propose 同步）。
任何其他动作（写代码、建 worktree）都是违规。
